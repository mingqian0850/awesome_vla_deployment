# 真机停顿与推理方式查表

[首页](../../README.md) · [English](../deployment-decisions.md) · [问题索引](decision-tables.md)

**允许工序停顿时，可以先用同步推理；是否需要异步取决于停顿预算、控制模式和场景变化速度。**“卡顿”在这里指策略动作块之间的等待，不代表底层伺服、平衡或接触控制可以停止。本页是工程决策与验收方法，不是某台机器人的控制许可。

<a id="select"></a>
## 按条件选择

| 我的具体情况 | 优先尝试什么 | 必须做什么 | 什么时候换方案 |
| --- | --- | --- | --- |
| 静态工位，动作块之间允许等待，控制器支持经过验证的等待状态 | 同步：观测 → 推理 → 执行选定步数 → 再观测 | 等待时继续运行底层控制；测量每次停顿及完整工序节拍 | 停顿超预算、等待时发生滑移，或执行时观测已过旧 |
| 放好工件后可停，抓取、插入或搬动过程中不可停 | 按工序阶段切换策略 | 明确阶段进入/退出条件；只在已验证状态等待 | 阶段识别不可靠，或不能保证抵达允许等待的位置 |
| 场景变化较慢，但块间不能停 | 推理与执行重叠，维护有界动作缓冲 | 测量剩余有效缓冲、尾延迟和新旧块切换；处理旧响应 | 队列不断变长、动作过旧、切换抖动或经常耗尽 |
| 传送带、移动物体或接触状态变化快 | 优先缩短感知到执行延迟及每次承诺执行的步数 | 为动作设观测年龄上限；用新观测重规划并验证响应 | 异步虽平滑却持续执行过期动作；需改感知、模型、算力或控制分工 |
| 人形行走、动态平衡或持续力控 | 保持适合该机器人的连续底层反馈控制，策略输出经接口接入 | 核实策略控制的是目标、速度还是力矩；验证看门狗与失联响应 | 不知道接口超时语义时，先补齐接口验证，不能按“允许停顿”配置 |
| 远端 GPU，网络抖动明显 | 本地控制与超时处理，加有截止时间的推理请求 | 把传输与排队计入延迟；标记观测时间与请求序号，拒绝过期响应 | 无法满足截止时间时，调整本地推理、执行策略或工序预算 |

异步队列、动作块融合与 RTC 不是同一个功能。异步让计算和执行重叠；融合处理重叠预测的组合；RTC 类方法还涉及已承诺动作的条件化。不能只开启一个队列，就声称具备另外两者。进一步原理见[实时推理](41-real-time-inference.md)。

<a id="pause"></a>
## 允许停顿：具体先做这五件事

1. **定义“允许”的边界。** 记录可停的工序、最长单次等待、允许的整周期节拍，以及工件在等待时是否会移动、掉落或持续受力。未知值先测量。
2. **确认等待接口。** 位置目标保持、受控停止、柔顺等待等行为取决于控制器。持续发送上一条速度或力矩可能继续运动，断开控制也不等于安全停止。选择设备支持并验证过的行为，参见[运行防护](43-safety.md)。
3. **建立最简单的同步循环。** 采集带时间戳的观测，推理得到 H 步动作，执行选定的 s 步（s ≤ H），按定义进入下一次观测和推理。底层反馈控制始终独立运行。
4. **记录全过程。** 至少记录观测采集、请求发出、响应收到、首条/末条命令交付，以及下一块首条命令时间。若能读取设备反馈，再记录实际执行时间；命令发出不等于电机已执行。
5. **注入慢响应和失联。** 先用回放或模拟接口测试等待、超时及恢复时重新观测的路径，再在受控设备测试中确认。通过条件包括任务成功、等待预算、动作新鲜度、恢复无突跳。

没有必要仅因别人使用异步，就先增加队列与并发复杂度。同步基线不满足以上条件时，依据测量结果改方案。

<a id="budget"></a>
## 用数字判断：卡顿来自哪里？

下列是工程量，**不是各框架通用的参数名**。在自己的执行器、请求客户端和控制器配置中分别实现。

| 量 | 定义与配置位置 | 用它检查什么 |
| --- | --- | --- |
| f、T=1/f | 策略动作交付频率与间隔；执行器时间基准。不是伺服内环频率 | 一块动作实际能覆盖多久 |
| H、s | 模型预测步数、每次实际执行步数；模型配置与执行循环 | 大 H 不表示一定执行整块；增大 s 会延长开环时间 |
| L | 从观测采集到可用动作的延迟，包含预处理、排队、网络与后处理 | 平均值、p95/p99、最大观测值及长尾来源 |
| B | 新请求发起时队列里剩余的有效动作时间 | 重叠执行能否撑到新结果到达；不能用原始整块长度代替 |
| A_max | 工序容许的最大观测年龄；动作接收/执行检查 | 结果到达时和实际使用时是否已经过期 |
| P_max | 当前工序允许的最长额外等待；等待状态和看门狗 | 同步停顿或异步耗尽能否接受 |

**演算示例，非推荐参数：** f=50Hz，所以 T=20ms；H=10，但每次只执行 s=5；观测到首动作可用 L=76ms。假设马上开始交付，5 条命令的时刻为 76、96、116、136、156ms，因此第 5 条使用的观测已经是 156ms 前的。若随后等待一个时间格，在 176ms 重新采集并同步推理，下一块首条命令在 252ms，两个块的命令间隔是 96ms，比正常 20ms 多等待 76ms。

若另一个重叠方案在发起请求时还剩 B=100ms 有效动作，L=76ms 仅留下 24ms 余量。延迟变成 130ms 就超出缓冲 30ms。`L + 未计入的抖动/交付余量 < B` 是避免缓冲耗尽的必要预算检查，**不能保证动作仍新鲜、块间连续或机器人稳定**。统计分位数也不是硬实时保证；超过预算仍需明确处理。

<a id="acceptance"></a>
## 看到什么现象，下一步做什么？

| 现象 | 先检查 | 处理与通过条件 |
| --- | --- | --- |
| 平均推理很快，偶尔明显停顿 | p99/最大延迟、网络重传、首轮编译、队列耗尽时间 | 分开统计预热与稳态；调整慢环节或等待策略；故意慢响应仍进入预期状态 |
| 队列从不空，但机器人反应越来越慢 | 队列长度、观测时间、请求顺序 | 限制缓冲时长并拒绝过期响应；验证年龄不累积。替换已承诺动作需验证连续性 |
| 每次新动作块到来都会跳一下 | 切换前后的目标差、坐标/归一化约定、重叠步含义 | 先修语义，再评估连续切换方法；仅加平滑可能引入延迟或改变接触行为 |
| 允许等待，但工件滑落或插入受力持续增长 | 夹持/接触状态和等待控制模式 | 该阶段尚不满足“可停顿”；重新定义阶段与控制行为后再测 |
| 断网恢复后突然执行旧动作 | 请求序号、采集时间、队列恢复规则 | 失效响应不进入执行队列；恢复先获取新观测，并通过设备支持的恢复流程 |

交付记录应包含：工序及控制模式、时间戳定义、延迟分布、最大实测停顿、最大实测观测年龄、超时次数/响应、任务成功次数/总次数。不要只报“模型推理达到多少 FPS”。
